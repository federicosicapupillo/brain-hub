## PART A — Auto-verificabile

### A0. Severity Classification
- **Severity:** HIGH (touches the Execute pipeline and adds a new writer of `execute_receipts` / `execute_idempotency`).
- **Blast radius:** restricted to orphan recovery code paths; nominal Execute paths (Internal + External v3.35b) unchanged at the call surface (only an additional inline check is consulted when a row already exists with `receipt_id IS NULL`).
- **Reversibility:** all reaper writes are append-only (one recovery receipt + one idempotency-row stamping). No data is deleted.
- **Empirical evidence required:** YES — crash-injection test with DB assertions (delivered: `scripts/test-orphan-gate-reaper-v3.35c.py`, 33/33 PASS on live dev server).

### A1. Funzionalità
Implementato un **Orphan Gate Reaper** isolato come servizio server-side (`src/lib/execute-dispatcher/orphan-gate-reaper.server.ts`) e un endpoint dedicato controllato (`POST /api/recover-orphan-execute-gate`).

Comportamento per decisione:

| Decisione | Trigger | Effetto DB |
|---|---|---|
| `not_found` | nessuna riga `execute_idempotency` per (owner, key) | nessuno |
| `already_completed` | riga esiste con `receipt_id` non NULL | nessuno (ritorna receipt esistente) |
| `not_orphaned_pending` | riga `receipt_id IS NULL`, età < TTL | nessuno |
| `orphaned_failed` | LOW/MEDIUM scaduto | nuovo receipt `result='failure'`; idempotency row stamp |
| `orphaned_unknown_requires_manual_review` | HIGH / CRITICAL / unknown scaduto | nuovo receipt `result='failure'` con `requires_manual_review=true`; idempotency row stamp |
| `orphaned_recovered` | seconda chiamata su gate già recuperato | nessun nuovo receipt — replay del recovery receipt |

**Nessuna riesecuzione automatica del handler originale.** Il reaper non chiama mai l'external dispatcher, non contatta sandbox endpoint, non invoca handler internal. È puramente uno stamper di stato che converte la condizione di silenzio in audit esplicito.

### A2. Governance & RBAC
- **Nuovo permesso RBAC:** `recover_orphan_execute_gate`, aggiunto in `src/lib/governance/rbacModel.ts` al ruolo `user` (l'utente recupera solo i propri gate).
- **Governance Evaluator:** l'endpoint passa per `evaluatePermission()` come tutti gli altri endpoint Execute. Nessun bypass.
- **Auth boundary:** `owner_id` è derivato esclusivamente da `auth.uid()` ricavato dal bearer token. Eventuali campi `owner_id` nel body sono **ignorati** (verificato in Test G).
- **Eventi audit emessi:** `execute_orphan_gate_detected`, `execute_orphan_gate_recovered`, `execute_orphan_gate_failed`, `execute_orphan_gate_manual_review_required`, `execute_orphan_gate_reaper_skipped_not_expired`, `execute_orphan_gate_reaper_skipped_completed`.
- **Cross-user:** strutturalmente impossibile (la query è scoped da `auth.uid()`); 401 senza token.

### A3. Stato dei dati
- **Migration:** **NESSUNA.** Lo schema esistente di `execute_idempotency` (con `receipt_id uuid NULL`) e di `execute_receipts` (`result text CHECK in ('success','failure','blocked')`) è sufficiente.
- Lo stato di un gate orfano è rappresentato da: `receipt_id` ora popolato + il receipt punta a un record con `audit_record.orphan_gate_status ∈ {orphaned_failed, orphaned_unknown_requires_manual_review}`.
- **Decisione di non estendere il CHECK constraint** motivata: aggiungere stati al receipt avrebbe richiesto migrazione distruttiva del CHECK e duplicazione di semantica già esprimibile via `audit_record` JSON. Il reaper usa `result='failure'` per ogni recovery non-success, distinguendo HIGH via `audit_record.requires_manual_review=true`.
- **Side effect su dati:** solo INSERT su `execute_receipts` e UPDATE di `receipt_id` su `execute_idempotency` (gate-first conditional update: `... WHERE receipt_id IS NULL`). Nessun DELETE.

### A4. Performance & Resilienza
- **TTL costante:** `EXECUTE_ORPHAN_GATE_TTL_MS_DEFAULT = 60_000` ms (60s) per runtime reale; override per test via parametro `ttl_ms` (test harness usa `1000` ms).
- **Polling:** il reaper è chiamato puntualmente; nessun loop infinito. Una singola invocazione completa in <100ms (verifica empirica del test harness).
- **Race su recovery:** gate-first update con clausola `WHERE receipt_id IS NULL` garantisce che la prima recovery vince; chiamate successive cadono in `orphaned_recovered` (replay). Verificato in Test H.
- **Resilienza ai retry del client:** verificato in Test F (already_completed) e H (idempotency del reaper stesso): nessun receipt duplicato anche con 3+ invocazioni consecutive.

- `tsgo --noEmit` → **PASS** (exit 0, no diagnostics).
- `npm run build` → **PASS** (exit 0, `✓ built in 11.82s`, Nitro worker generato senza errori).

### A6. Limiti residui
- **HIGH non rieseguibile automaticamente, by design.** I gate HIGH/CRITICAL scaduti restano marcati `orphaned_unknown_requires_manual_review` finché un operatore umano non interviene. **In v3.35c non esiste UI/endpoint per chiudere manualmente un manual-review.** Il manual-review è registrato ma non risolvibile via UI.
- **Reaper schedulazione:** v3.35c espone il reaper su invocazione esplicita (endpoint + chiamata inline al riconoscimento di un gate orfano). Non c'è ancora un job periodico che scansiona globalmente i gate orfani. Un client che non riprova mai una chiave orfana non triggera mai la recovery di quella chiave. **Questo è un limite dichiarato, non un bug.**
- **`auto_reexecuted` è sempre `false`** in v3.35c — garanzia di patch, non limite da rimuovere.

### A7. Debito tecnico introdotto
- **Test harness:** `scripts/test-orphan-gate-reaper-v3.35c.py` lascia righe in `execute_idempotency` / `execute_receipts` perché `psql` nell'ambiente sandbox è SELECT/INSERT only. Mitigato: chiavi sono UUID univoche per run, nessuna collisione tra esecuzioni.
- **Endpoint `recover-orphan-execute-gate`:** non c'è UI lato Brain Hub che lo invoca esplicitamente. Resta accessibile solo via API. Nessun pulsante di "force recovery" — coerente con principio di sicurezza.
- **TTL hard-coded a 60s** nel modulo: facile da modificare ma non è ancora un config DB. Acceptable.

### A8. Debiti ereditati
- **Da v3.35a.1 / v3.35b — winner crash → gate orfano:**
  - **RISOLTO per LOW/MEDIUM:** il gate viene riconosciuto come orfano dopo TTL, stampato con receipt esplicito (`orphaned_failed`), nessuna riesecuzione automatica. L'idempotency row non è più bloccata in stato `pending` indefinito.
  - **RISOLTO per HIGH/CRITICAL come stato esplicito, NON come riesecuzione:** il gate viene marcato `orphaned_unknown_requires_manual_review` con receipt; il pending non è più infinito (è "manual-review pending", non "silenzio"); la riesecuzione automatica è proibita per design.
  - **RIMANE fuori scope:** la chiusura manuale del manual-review (richiede dashboard operatore — outside v3.35c).
- **Non esistono più casi noti di pending infinito silenzioso** una volta che un client riprova la chiave o un job/operatore invoca il reaper sulla chiave. L'unico "pending residuo" oggi è il manual-review HIGH, ed è esplicito a livello DB.
