# EQG Report — v3.35b External Execute Sandbox Foundation

Patch: **v3.35b — External Execute Sandbox Foundation**
Scope: open the first level of external execute (LOW-risk sandbox only),
end-to-end through registry → governance → confirm → idempotency →
artifact → handler → receipt. NO orphan-gate reaper, NO HIGH actions,
NO real external rollback.

---

## Part A — Engineering Quality Gate (A0–A8)

### A0. Severity Classification

| Aspect                  | Classification |
| ----------------------- | -------------- |
| Patch type              | Foundation / new execution surface |
| Risk profile            | LOW (single sandbox action, no business side-effects) |
| Reversibility           | N/A — sandbox endpoint is idempotent and stateless |
| Blast radius            | One owner_id at a time, scoped via RLS |
| Schema changes          | None |
| Security-sensitive code | Yes — auth, governance, redaction, idempotency |
| Severity (overall)      | **Medium** (security surface, even if action is LOW) |

### A1. Funzionalità

- Implementato **single allowlist registry** (`src/lib/execute-dispatcher/external-registry.ts`) con un solo entry: `external_webhook_test_ping` (LOW, sandbox).
- Implementato **dispatcher esterno separato** (`src/lib/execute-dispatcher/external-dispatcher.server.ts`) — nessuna condivisione di handler con il dispatcher interno; mappa handler statica, niente lookup per stringa arbitraria.
- Endpoint HTTP unico: `POST /api/execute-external-action`.
- Endpoint sandbox di test: `POST /api/public/external-execute-sandbox-target` — risposta JSON deterministica, nessun side-effect, nessun segreto.
- Pipeline ordinata: registry → validation → confirm gate (live) → governance → idempotency gate-first → artifact → handler → receipt.
- Stati di output: `executed | replayed | rejected_unknown_action | rejected_disabled | rejected_validation | rejected_confirm | rejected_governance | rejected_high_risk_blocked | rollback_not_supported | failed`.

### A2. Governance & RBAC

- Aggiunta azione `execute_external_action` a `RBAC_PERMISSIONS.user.allowed_actions` e `requires_confirmation`. `max_risk_level` resta `medium`, quindi LOW passa e HIGH è bloccata già al livello policy.
- Il dispatcher chiama `evaluateAction({ action: "execute_external_action", entity: { type: "user", id: userId }, risk_level: <registry> })`. Nessun bypass possibile: il path è unico.
- HIGH/CRITICAL sono **doppiamente** bloccate: (i) nessuna entry HIGH in registry, (ii) early-return `rejected_high_risk_blocked` nel dispatcher.
- Confirm gate (riusa pattern v3.35a.1): per `live_execute=true` richiede `confirmed_at` ISO entro 5 minuti **e** `confirmation_id` non vuoto. Dry-run non richiede confirm.

### A3. Stato dei dati

- **Nessuna migration**: si riusa `internal_execute_artifacts`, `execute_receipts`, `execute_idempotency` di v3.35a.1.
- Artifact: `title` prefissato `[external] …`, `payload` JSONB con `execute_scope: "external"`, `external_action_type`, `connector_name`, `handler_name`, `dry_run`, `live_execute`, `confirmation_id`, `request_hash`, `payload_preview_redacted`.
- Receipt: `audit_record` JSON con tutti i metadati richiesti dal contratto (execute_scope, external_action_type, connector_name, handler_name, risk_level, dry_run, live_execute, confirmation_id, idempotency_key, request_hash, payload_preview_redacted, response_preview_redacted, http_status, timing_ms, rollback_supported). `external_reference` popolato da `x-correlation-id` della risposta sandbox quando presente.
- Deviazione dichiarata: la tabella `internal_execute_artifacts` mantiene il nome storico ma ospita ora anche artifact esterni (discriminati da `payload.execute_scope`). Non è stata creata una tabella separata per evitare migration in una patch foundation. Refactor naming previsto quando il volume esterno lo giustificherà.

### A4. Performance & Resilienza

- Timeout esplicito per fetch live (`registry.timeout_ms = 5000`) tramite `AbortController`.
- Dry-run: nessuna chiamata di rete.
- Idempotency **gate-first**: insert prima del side-effect, stamping con `receipt_id` dopo writeReceipt. Race convergence con polling 20×100 ms (riuso v3.35a.1).
- Tutti gli `await` ai limiti DB sono protetti — failure path scrive sempre un Receipt `failure` (governance, artifact, handler) e timbra il gate per non lasciarlo NULL.
- Empirical timing (test live, vedi sezione "Test Evidence"): dry-run end-to-end ≤ 110 ms; live sandbox ≤ 75 ms (timing_ms = 6).

### A5. Type Safety

- `tsc --noEmit` (tsgo) **PASS** dopo l'integrazione.
- `ExternalActionEntry` `Object.freeze` + `Readonly`. Registry è `Readonly<Record<string, …>>`.
- `validateExternalPayload` restituisce union narrato; nessun `any`. Sensitive-field check eseguito sul payload **e** sui nomi di campo per intercettare leak espliciti.
- Cast esplicito `as unknown as ExecuteReceipt["action_type"]` dichiarato come debito di tipi (vedi A7) — necessario finché il tipo `action_type` del receipt accetta solo `InternalActionType`.

### A6. Limiti residui

1. **Orphan Gate Reaper — non implementato.** Se il worker crasha tra l'insert del gate (step 5) e lo stamping del `receipt_id` (step 8), la riga in `execute_idempotency` resta con `receipt_id = NULL`. Comportamento attuale: i peer concorrenti polling per 2 s e poi falliscono con `failed`. **Non risolto in v3.35b. Rinviato a v3.35c.** Inherited da v3.35a.1.
2. **External rollback — non implementato.** `external_webhook_test_ping` ha `supports_rollback=false` per design (è una ping idempotente). Nessun endpoint `/api/rollback-external-action` viene esposto in v3.35b; un eventuale tentativo non passa nemmeno dal dispatcher. Documentato come fuori scope.
3. **UI — minima/assente.** Nessuna nuova route UI introdotta. Verificabilità affidata allo script di test (v. "Test Evidence"). Pannello "External Execute" candidato per v3.35c, includerà l'avviso "Orphan Gate Reaper not implemented — scheduled for v3.35c" e "HIGH external actions blocked".
4. **Sandbox target same-origin.** L'endpoint live colpito è ospitato dallo stesso server (`/api/public/external-execute-sandbox-target`). Sufficiente per validare il circuito; un target di terze parti reale verrà introdotto solo con un connector dedicato e relativo trust model.
5. **Crash-fault testing non eseguito.** Il test D verifica la convergenza idempotente in condizioni nominali (8 richieste concorrenti, tutti i peer arrivano). Lo scenario "winner crash tra gate insert e receipt stamping" non è stato simulato empiricamente in v3.35b — l'unico modo per chiuderlo è il Reaper di v3.35c + un test mirato.

### A7. Debito tecnico introdotto

- **Type cast `string → InternalActionType`** nel writer del receipt esterno: `ExecuteReceipt.action_type` è ancora tipato come `InternalActionType`. Refactor: generalizzare `ExecuteReceipt` a `InternalActionType | ExternalActionType` in v3.35c.
- **Artifact table sharing**: `internal_execute_artifacts` ospita anche artifact esterni. Discriminator solo a livello `payload.execute_scope`. Refactor: rename / view dedicata in v3.35c o successivo.
- **Polling 2 s per gate convergence** (ereditato): aumenta latenza p99 dei replay durante un winner crash. Reaper in v3.35c chiuderà il caso.

### A8. Debiti ereditati

- **Winner crash → orphan gate** (da v3.35a.1): non risolto in v3.35b, rinviato a v3.35c (Orphan Gate Reaper isolato + test crash mirato).
- **HIGH external actions**: non abilitate in v3.35b; restano bloccate sia in registry sia nel dispatcher.
- **Nessuna azione esterna irreversibile** è esposta in questa patch (no commit, no PR, no email, no social, no pagamenti).
